Beauty Center Management App: Feature Specification

Back-office app for a beauty and aesthetics center in Turkey. Covers employees, customers, treatments, sales and inventory, with an AI consultation assistant. Stack: ASP.NET Core, React and Microsoft SQL Server.

Draft v0.3, 12 Nov 2026. Working name: Victoria. Türkçe sürüm

ASP.NET Core (.NET 9/10) Web API React + TypeScript (Vite) MSSQL + EF Core Provider-agnostic AI Turkish + English UI TRY · KDV · KVKK

Overview & scope

Victoria is an internal back-office web app for one beauty and aesthetics center in Turkey. The center offers skin care and spa treatments, laser epilation, medical aesthetic treatments, and sells beauty products. Only the owner, managers and employees use the app; customers have no access. It is not meant to replace a full HR, ERP, accounting or CRM product. It answers five day-to-day questions:

Who did what?

Which employee performed which treatment, sold which product, and (optionally) what commission they earned.

What did the customer get?

Full treatment history: services, laser parameters per session, products bought, consents, before/after photos, package sessions left.

What should we recommend?

During a visit the employee asks the AI assistant, which combines the customer's profile with product and service descriptions.

What do we have?

Stock of retail products and consumables (with lot and expiry), how treatments use them, and when to reorder.

How are we doing?

Sales and revenue per service, product, employee and period, plus AI summaries.

Connecting modules. The three requested modules (employees, customers, inventory) need connecting modules before they produce useful data: Appointments (customer + employee + device + time), Service catalog (what is sold, what it consumes, how it is described), and Sales/POS (where money and stock movements are recorded). All are MVP.

Out of scope

  • Anything customer-facing: online booking, customer portal, mobile app for customers.
  • Full accounting, payroll and HR. Data is exported to the accountant (mali müşavir) instead.
  • E-commerce web shop.
  • Built-in card processing. The app records the payment method; the POS terminal stays separate.

Implement as permission-based access rather than hard-coded role checks. Roles are bundles of permissions (e.g. sales.refund, customers.health.view, commission.view.own), so the owner can adjust them without code changes.

Architecture

Frontend: React (same stack as the reconciliation app)

  • React 19 + TypeScript 5.9, Vite 7, ESLint 9
  • UI: Ant Design 5 (+ @ant-design/icons) with Tailwind CSS 4; icons: lucide-react; font: Geist
  • Same theme tokens: slate sider #0f172a, indigo primary #4f46e5, shared PageHeader, StatCard, StatusPill patterns
  • Server state: TanStack Query 5; HTTP: axios; validation: zod 4; dates: dayjs
  • Routing: react-router-dom 7; i18n: i18next + react-i18next + browser language detector, with tr (default) and en
  • Charts: Recharts; live updates: @microsoft/signalr; auth: oidc-client-ts if an identity provider is used
  • Calendar: FullCalendar resource time-grid (new dependency; not in reconciliation)
  • Same feature-sliced folders: app / pages / features / shared / lib
  • Clickable HTML prototype in prototype/

Backend: ASP.NET Core

  • Web API with a modular monolith: one project, one folder per module
  • EF Core + migrations; FluentValidation
  • ASP.NET Core Identity + JWT (access + refresh tokens)
  • Hangfire or Quartz for background jobs (SMS reminders, AI digests, stock and expiry checks)
  • SignalR for live calendar updates
  • Serilog + OpenTelemetry for logs and traces

Database: MSSQL

  • Azure SQL (one database); BranchId kept for future branches
  • Soft delete + audit columns on every table
  • Stock is a ledger (StockMovement), not a single editable number
  • Read-only SQL views for reporting and AI tools
  • Azure Blob Storage for photos and consent PDFs; DB holds only metadata
  • Optional later: SQL Server vector type or Azure AI Search for semantic product search

Pluggable integrations

  • IAiProvider: chat, tool calling, structured output, embeddings
  • INotificationChannel: SMS now; WhatsApp and e-mail later
  • IInvoiceProvider (Later): e-Arşiv / e-Fatura through a GİB-authorised integrator (özel entegratör). MVP uses a "manual" implementation: receipt number + uploaded photo
  • Each adapter is selected by configuration and covered by a fake for tests

Core business flow

This flow ties all modules together. Every report and AI feature depends on it being recorded correctly.

Customer calls / walks in→ Appointment
service + employee + device + time→ SMS reminder→ Check-in
questionnaire, consent check→ Consultation
AI recommendations→ Treatment
parameters, photos, consumables→ Checkout
+ recommended products→ Payment
+ receipt photo→ Stock deducted
activity / commission recorded→ Next session booked

Each sale line stores the employee who performed or sold it, and, when it came from the assistant, the AI recommendation it came from. Employee reports, commission and recommendation conversion all use these fields.

Goal: while a customer is at the center, any employee can open the customer and get well-reasoned service and product recommendations in seconds, even without deep product knowledge. Recommendations are grounded in the center's own catalog and the customer's record.

Data sent to the AI provider

  • Customer: pseudonymised ID, age range, skin type, concerns, recent treatments, recent purchases. No name, phone or TCKN.
  • Health data (allergies, contraindications) is used by the deterministic filter on our server and is not sent unless the customer gave explicit consent for AI processing.
  • Catalog: filtered candidates with their content fields, price and stock.
  • Sending data to a provider abroad is a cross-border transfer under KVKK. Choose a provider with a suitable contract and region, and check with a lawyer (see remaining questions).

The UI always shows: "AI suggestion: check before recommending. Not medical advice." Medical aesthetic treatments are suggested only as "discuss with the physician".

Provider-agnostic design

public interface IAiProvider
{
    Task<AiResponse> CompleteAsync(AiRequest request, CancellationToken ct);      // chat + tools
    Task<T> CompleteStructuredAsync<T>(AiRequest request, CancellationToken ct);  // JSON schema output
    IAsyncEnumerable<AiChunk> StreamAsync(AiRequest request, CancellationToken ct);
    Task<float[][]> EmbedAsync(IReadOnlyList<string> texts, CancellationToken ct); // optional
}
// Adapters: AnthropicProvider, OpenAiProvider, AzureOpenAiProvider, GeminiProvider, FakeProvider (tests)
// appsettings: "Ai": { "Provider": "Anthropic", "Model": "...", "MonthlyBudgetTry": 2000, "Features": { ... } }
  • Prompts are stored as versioned templates (TR and EN), not hard-coded, so they can be tuned without redeploying.
  • Each feature can use a different provider/model (e.g. a cheaper model for SMS drafts).
  • Every call is logged in AiInteraction: feature, provider, model, prompt version, tokens, cost, user, latency.
  • A small evaluation set (sample customers with expected safe recommendations) is run when switching provider or prompt version.
  • The app works fully without AI; each AI feature has its own on/off switch.

Non-functional requirements

Security

  • HTTPS only; JWT with short-lived access tokens and refresh rotation
  • Policy-based authorization on every endpoint
  • 2FA for owner and admin
  • Rate limiting on login; account lockout
  • Secrets in Azure Key Vault, never in the repo

KVKK compliance

  • Health data and photos are special-category data: explicit consent, restricted access, access logging
  • VERBİS registration and KVKK notice (aydınlatma metni) are the owner's responsibility; the app stores which version each customer saw
  • Cross-border transfer check for cloud region and AI provider
  • Retention and deletion policy; anonymise on request
  • Encryption at rest and in backups

Reliability

  • Automated daily backups with point-in-time restore, tested restore
  • Concurrency control (rowversion) on appointments, stock and packages
  • Idempotent checkout and invoice creation (no double sale or double invoice)
  • Retry queue for SMS and AI calls

Usability

  • Tablet-first in treatment rooms and at the desk
  • Checkout in under 30 seconds for a standard visit
  • AI recommendations in under 5 seconds (streamed)
  • Turkish formats: dd.MM.yyyy, 1.234,56 ₺

Performance

  • Calendar day view loads in < 1 s
  • Indexes on phone, appointment date, product, lot expiry
  • Heavy reports on views or pre-aggregated tables

Quality & DevOps

  • Unit tests for commission rules, stock, packages and the AI safety filter
  • Integration tests with Testcontainers (SQL Server)
  • CI/CD (GitHub Actions or Azure DevOps) to dev, staging and prod
  • Docker for local development

Remaining questions

All earlier questions are answered (see Decisions). These are deferred, not blocking the MVP:

  • AI provider and data transfer: the app serves Turkey only, but if the chosen AI provider processes data outside Turkey, that is still a cross-border transfer under KVKK. Before enabling AI on real customer data, pick the provider/region and have the transfer basis and AI consent text checked. The consultation assistant can run without health data in the meantime.
  • SMS provider: choose the provider and sender ID (başlık) before go-live; register in İYS before sending any commercial SMS.
  • Commission rates: enter them when the owner decides to turn commission on.
  • e-Arşiv integrator: choose one when the manual receipt upload becomes too much work.
